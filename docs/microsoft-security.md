# Microsoft directory connection

This installation can connect one Microsoft Entra application with client credentials. The principal first reviews Microsoft's terms in Provider charges and then approves the `directory:read` capability. Configure `ENTRA_TENANT_ID`, `ENTRA_CLIENT_ID`, `ENTRA_CLIENT_SECRET` and a `SESSION_SECRET` of at least 32 characters in runtime secrets. These values are never entered through a Satchel route. The principal must verify the Entra application has only the Microsoft Graph **application** permission `User.Read.All` and tenant administrator consent. Do not grant mail, calendar, file or site content permissions. Satchel requests the Graph `.default` scope; its limited endpoint does not reduce permissions that an administrator independently grants to that application.

Connection uses the configured tenant's fixed `login.microsoftonline.com` token endpoint. A read uses only `GET https://graph.microsoft.com/v1.0/users?$select=id,displayName&$top=100`. It returns the first page and reports whether more entries exist; it never follows a provider-supplied continuation URL. Access tokens are opaque and validated by Graph. Satchel does not implement interactive Microsoft sign-in, delegated consent, email, calendar, file or site access.

The connector caches the access token using authenticated encryption through `integration-secrets` with a Microsoft-specific derivation domain. The client secret remains in runtime configuration. A Graph authorization refusal wipes the cached token and refuses queued work. Expired tokens require an explicit reconnect; no refresh or automatic token exchange occurs. Reconnecting advances a generation, wipes the prior cache and refuses queued reads. Revoking does the same and marks work already in flight uncertain. Microsoft application credentials and administrator consent must be revoked separately in Entra if the application itself should lose access.

Read jobs retain the approving operator, native session and operator version. Execution checks current owner status, active firm membership when present, the originating session's expiry and revocation, provider session generations and pins, provider review, configuration fingerprint, token expiry and connector generation. A transaction claims each queued job before the request and checks the authority again before releasing its response. A lost response, changed authority in flight or interrupted worker produces an uncertain journal entry and never an automatic retry. An interrupted worker is classified after the bounded request's timeout window. A new read requires a newly queued job.

Only directory IDs and display names are returned in the authorized execution response. Job state and audit records retain normalized outcomes, HTTP status, counts and timing, without directory bodies, tokens, provider error bodies or exception text. A completed job cannot replay its directory response. The two installation-local tables `s_microsoft_connector` and `s_microsoft_jobs` must be excluded from portable archives and never imported during restore; they carry credentials and native session authority. Safe audit events remain portable.

Routes are `GET /security/microsoft`, `POST /security/microsoft` with `{ "approved": true, "capability": "directory:read" }`, `POST /security/microsoft/jobs` with `{}`, `POST /security/microsoft/jobs/:id/run` with `{}`, and `POST /security/microsoft/revoke` with `{}`. All require a person with current native owner authority. The API prefix is `/api/satchel`.

The provider protocol is documented in Microsoft’s [client credentials flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow) and [list users API](https://learn.microsoft.com/en-us/graph/api/user-list?view=graph-rest-1.0). The held shared sandbox application has additional directory permissions; its live receipt proves Satchel’s limited operation and local revocation, not least privilege of that external registration or a licensed Microsoft 365 workload.
