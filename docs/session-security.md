# Authenticator and device access

Open Team & safety, then Security settings and Authenticator and devices. Enter a new security passphrase of at least twelve characters, add the displayed setup key to a time-based authenticator and confirm with the passphrase and a current six-digit code. The setup key is shown only during enrollment. Once confirmed, every other native session must prove both factors before opening private screens, API routes or native credential controls. Email confirmation alone cannot bypass that check.

Passphrases are stored only as salted PBKDF2 hashes. Authenticator seeds use authenticated encryption under an installation-local derivation of SESSION_SECRET. Enrollment and confirmation are fenced against a concurrent device revocation or enrollment. Codes cannot replay between sessions. Failed attempts are limited across the person's sessions; repeated failures pause further attempts for five minutes. Successful confirmation is bound to the current native session. Its expiry, operator version and revocation still apply.

Signed-in devices lists the current person's native sessions. End device access revokes the selected session through native authorization and records a safe action audit. A person cannot revoke another person's device without native administrative authority. Queued Microsoft reads also retain their originating native session; ending that session prevents later execution, including after a restart. A request already claimed can be uncertain, and its result is withheld after authority changes.

Keep an authorized device available while confirming enrollment on another device. There is no email-only factor reset or automatic recovery path. Losing both factors needs an installation administrator's controlled recovery; that recovery door is not implemented by this clause. Changing SESSION_SECRET also requires a planned migration of existing encrypted factors; no automatic decryption fallback is provided.

Firm archives exclude authenticator seeds, password hashes, session confirmations, Microsoft credentials and credential-bound jobs. Safe security and connector audit actions remain exportable under current audit authority. Restoring into an empty installation imports no authority to execute a connector job. Microsoft configuration and its administrator consent remain the installation owner's responsibility; see [Microsoft directory connection](./microsoft-security.md).
