## BILL-012

**Exact receipt and write-off rules.** **CT policy approved with riders, 26 October 2026; implementation status unchanged.** For BILL-012 offline-payment shortfalls, finance approval means explicit approval by the active principal of the exact current invoice revision, exact positive integer USD-cent amount and recorded reason. Approval and posting retain the invoice identity and revision, amount, reason, approving person and approval time in linked append-only history. A changed revision, amount or reason requires fresh approval; current authority, matter access and ethical walls are checked at the server when posting. Billing staff may record receipts but cannot approve write-offs; lawyer, accountant or trust-officer status alone, custom roles, agent keys and integration keys confer no write-off approval authority. A write-off reduces the collectible receivable and records no payment, bank deposit or trust movement; original invoice artifacts and approvals remain unchanged. Later receipts allocate only against the remaining collectible amount, with excess retained as unapplied client credit. A bounced or stopped check reverses only the original payment allocations through linked append-only entries; it does not reverse an independently approved write-off. Invoice due, aging and collection resume only for the resulting collectible balance, without repeating sent reminders. The complete target includes a separately principal-approved, reasoned, exact-revision, append-only reversal naming the original write-off and amount, preserving both records and restoring the corresponding collectible balance exactly once. That reversal path remains a named Gap until implemented and proved. BILL-016 refuses a void while an unreversed write-off remains; until the approved reversal path is implemented and proved, such an invoice cannot be voided. Posting a write-off reversal does not bypass any existing payment-resolution, counsel-review or void prerequisite. Refunds remain subject to BILL-007 approval. ## CONNECT-001

**Connector and security mechanism.** Documented versioned APIs and signed webhooks expose permitted matters, tasks, documents, deadlines and finance events with pagination, scopes, idempotency and delivery journals. Agent credentials cannot approve legal work, move funds or escalate their own access. The principal creates each integration with an explicit existing-matter allow-list and per-resource read capabilities; each read and delivery intersects those with the sponsor’s current active access and document ACL. A preparation capability creates only matter-bound bill/deadline proposals, with an atomic request-key replay record; SAT-009 keeps its separate new-matter preparation door. Only the principal may enter a webhook destination. The current outbound rule checks HTTPS on port 443, rejects credentials/fragments, reserved hostnames and non-public literal addresses, and uses Workers fetch with redirects refused. There is no separate DNS preflight and no application address pin; resolved-address/pinned egress remains the named Base egress-door Gap, and CONNECT-001 stays partial until adoption. FIRM-004 declares this metadata-only outbound flow and inherits the same named gap. Opt-in metadata events contain only stable IDs, type and time; HMAC-SHA256 covers attempt Unix seconds, event ID and exact body. Receivers use a five-minute replay window and deduplicate by event ID; at-least-once delivery never claims exactly-once processing. Every attempt is journaled; five consecutive failed or uncertain deliveries pause until principal resumption. Rotating credentials replaces the API key and sealed signing secret, invalidates the old key and pauses delivery while the receiver changes its secret; revocation stops new claims while an already claimed request may have reached its destination. Secrets and credential-bound queues are installation-local and absent from archive/API listings; the normal action audit retains safe outcomes.
